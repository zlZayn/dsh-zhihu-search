# 决策：结果语义对齐（D1–D4）与契约测试机制（2026-09-14）

已实施。

## 问题

四件事都源于同一类错位：**参数面承诺的语义，与上游实际做到的语义不一致**。

1. **D1 `minValue`**：说明写的是「只要点赞数 ≥ N 的结果」，实测区间只筛「本次检索到的候选」——
   同查询同下限，`count=3/5/10` 分别得 1/1/3 条，且恒为前 `count` 条的子集。
   于是「知乎没有高赞内容」这种错误结论会被模型照着说出去。
2. **D2 `site`**：`host` 是整串精确匹配（`host=="qq.com"` 取不到 `news.qq.com`），
   而参数说明承诺「传完整 URL 会自动剥成域名」—— `www.github.com` 因此静默返回 0 条。
3. **D3 `EmptyReason`**：只在 `Items` 为空时出现，取值恒为「无相关内容」，被过滤空时也不解释原因。
4. **D4 参数面与输出面不对称**：`sortField` 能按评论数与时间排序，输出里却没有这两个读数。

## 决策

- **D1**：带下限时按**端点上限取候选池**（`FILTERED_CANDIDATE_COUNT = MAX_COUNT`，不是字面量 10），
  筛完再按模型要的条数截断；缓存里存**未截断的池子**（否则 `count=3` 会污染 `count=10`）。
  渲染层在「筛后条数 < 请求条数」以及「带下限却 0 条」两种情况下说明「下限只在本次候选内生效」。
  上界（`maxValue`）**刻意不暴露**：既然只是筛候选，`≤N 赞` 的收益远小于参数面变宽的成本。
- **D2**：`normalizeHost` 一并剥掉开头的 `www.`；参数说明写明「精确匹配，子站要单独写」。
- **D3**：删掉 `EmptyReason`——零诊断价值。探针结论与「什么情况下该把它加回来」记在
  [src/types.ts](../../src/types.ts) 与架构文档的偏差表里。
- **D4**：把 `commentCount` / `editTime` 加进 Canonical Output 与渲染（时间渲染成 `YYYY-MM-DD`）。
  **不改排序旋钮**：删参数按问题链是 major，补字段是 patch，而对称性两边都能满足。
  Token 成本实测估算：每条约 12–14 token，站内默认 5 条约 70，全网 20 条约 280 ——
  相对摘要本身（每条数百 token）是 1–3%。
- **防腐化**：把探针写成仓库里的**契约测试**（见架构文档「契约测试」一节），
  每周一由 `contract.yml` 跑，不进日常 CI。

## 替代方案

- **D1 只在描述里注明「筛的是候选」**：最省事，但模型仍会给出错误结论；且候选池白丢。
- **D1 暴露 `maxValue`**：能表达「点赞 ≤N」，但把它做成全库排序做不到的前提下，收益与参数面宽度不成比例。
- **D4 收回 `commentCount` / `editTime` 两个排序档位**：按问题链属 major（删参数），
  而补字段是 patch；且「按评论数找讨论」本身是真需求。
- **契约测试进日常 CI**：每轮约 16 次请求，日常提交会把配额烧在无关的漂移上；
  且契约漂移是周级信号。代价是「红了可能晚一周才看到」，由每周一固定跑 + 发版前手动跑覆盖。
- **契约测试复用 `src/` 的传输层**：省事，但插件的解析 bug 会同时污染被测对象与断言，变成自我印证。

## 影响

- 输出 schema 新增两个**可选**字段（加字段不是收紧，旧消费方不受影响）。
- 新增配置项 `streamTimeoutMs`；`Config.timeoutMs` 的默认值改为从 `transport.ts` 的常量取，不再各写一份。
- 直答工具的超时由「写死 60s」改为「流式预算 + 余量」，配置调大时不会先被 DSH 截断。
- 新增 `npm run test:contract` 与 [contract.yml](../../.github/workflows/contract.yml)；
  日常 `npm test` 仍排除 live 探针，只多一份底座的离线自检。
- 档位：**minor** —— 新增配置项与输出字段属于「旧用法仍正确、且能观察到新能力」（Q3 是）。
