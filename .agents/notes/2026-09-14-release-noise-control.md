# 决策：零行为变更不发版，并用路径守卫固化（2026-09-14）

已实施。

## 问题

发布规则此前只问「改动是否进入发布产物」，于是**纯文档与行为等价的内部重构也会消耗版本号**：
它们进了 `lib/`，却没有任何使用者可观察的变化。代价是用户的升级噪音与被浪费的 SemVer 空间。

## 决策

- 问题链的 **Q0 改为按行为判定**：改动是否改变**已发布产物的行为**（工具参数与描述、渲染文本、配置、导出面、构建产物）？否 → 不发版，改动搭下次发布的车。
- 判据是行为，不是路径：纯文档 / 测试 / CI / 工具脚本，以及**行为等价的内部重构**都归「否」。
- 机器只判得了一半，于是加一道**路径守卫** [scripts/release-guard.mjs](../../scripts/release-guard.mjs)：
  `release.yml` 在 bump 前比对「上个 tag..HEAD」的改动清单，只剩非产物改动就直接红；`force` 输入是唯一越过方式。
- `tag ⇔ npm 版本` 的一一对应**不破**：不发版就不打 tag，git 历史即归档。

## 替代方案

- **靠 commit 规范自动推断**（`[skip release]`、conventional commits 映射档位）：把定档权交给提交信息，而档位本来需要人按问题链判断；且规范一破就静默失效，比不设更糟。
- **只打 tag、跳过 npm 发版**：会造出第二类版本（有 tag 没包），所有「这个 tag 对应哪个包」的推理都要分叉；单一事实源被破坏。
- **只写进文档、不设守卫**：规则不可执行。这次的问题正是「纪律在人脑里」，而人会漏。
- **守卫解析 AST 判断行为等价**：做不到可靠，成本远超收益；改由 Q0 的人回答，守卫只兜住可判的那半。

## 影响

- 发版前多一步守卫；它在 `npm ci` 之前跑，失败即止，不浪费额度之外的任何东西。
- 行为等价的源码重构仍可能被误放行（守卫按路径判）—— 这是刻意的：**宁可漏判也不误拦**，未识别路径一律算「改变产物」。
- 已发布的 v1.4.2 只当历史，不撤回；Release 说明里补一句「无行为变化，无需升级」。
