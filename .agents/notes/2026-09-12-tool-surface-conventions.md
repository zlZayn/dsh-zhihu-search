# 决策：工具可见面按三槽写，且参数不得静默失效（2026-09-12）

已实施，随 v1.1.0 发布。

## 问题

模型选工具、填参数全靠工具描述与参数 schema。实测三处不足：

- `zhihu_zhida` 的工具描述列举了 `fast / thinking / agent`，而 `mode` 参数描述又列了一遍。参数 schema 每次请求都随描述一同进入上下文，第二遍是纯浪费。
- `zhihu_global_search` 指向了 `zhihu_search`，反过来没有。单向路由让「模型先读到哪个工具」决定路由质量。
- 更要紧的一处：`compileSortBy` 在 `sortField` 为 `default` 或缺省时直接 `return undefined`，**`minValue` 与 `order` 一起被静默丢弃**——而 `sortField` 的缺省值正是 `default`。

第三条不是文档问题。模型传 `minValue: 100` 想要「点赞 ≥ 100」，拿到的是未过滤结果，然后照着它回答：静默的错误答案，比报错糟得多。

## 决策

1. **工具描述按固定三槽写**：是什么 → 什么时候选它（含指向别的工具）→ 结果形态或硬边界。禁止在工具描述里枚举自己参数的取值。
2. **能力与枚举分界**：`可筛出高赞内容` 是能力、有路由价值，保留；`fast / thinking / agent` 是枚举，删掉。
3. **参数不得静默失效**：`sortField` 缺省或为 `default` 时，出现 `minValue` 或非默认 `order` 一律抛 `CompileError` 并带 hint。
4. 只拒绝 `order` 的**非默认值**。`order: 'desc'` 是文档写明的默认值，模型可能照抄；把「填了默认值」判成失败会制造假故障。

## 替代方案

- **`minValue` 缺 `sortField` 时自动按点赞排序**：零失败，但引入隐藏推断——模型想按评论数筛就会被猜错，且猜错无声。
- **只在参数描述里写明「不给 `sortField` 时无效」**：改动最小，但保留了静默错误答案这个最坏结果。
- **连 `order: 'desc'` 一起拒绝**：会把无害的默认值填充变成调用失败。
- **把三槽约定写成测试**：枚举值里含 `all`、`agent` 这类常见词，机械断言必然误报；因此约定落在 [docs/ARCHITECTURE.md](../../docs/ARCHITECTURE.md)，由评审约束，只把第 3 条固化成测试。

## 影响

- `minValue` 用错时多一次往返，换来模型能据 hint 一次纠正；测试以「一次 HTTP 请求都没发出」固化这条。
- 三份工具描述总长基本持平（约 300 → 330 字），没有靠写更长换效果。
- 约定写进 [docs/ARCHITECTURE.md](../../docs/ARCHITECTURE.md) 的「工具描述约定」，防止下次改描述时把枚举写回去。
