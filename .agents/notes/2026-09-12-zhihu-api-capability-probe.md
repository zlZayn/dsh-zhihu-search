# 决策：以生产实测校准知乎 API 能力（2026-09-12）

已实施。

## 问题

知乎官方文档与实际接口存在偏差，导致两条关键设计无法定论：

- `SortBy` 未出现在任何文档中，无法判断任务书要求的 `compileSortBy` 是真能力还是幻觉。
- 每日额度与限流策略未知，无法确定缓存与令牌桶的参数。

## 决策

直接用生产凭据对接口做受控探测，并把全部结论写成测试断言。

实测结果：

- 每日额度 **5000/天**（实名后）。此前为 10/天，相差 500 倍。
- `SortBy` **真实存在**且被校验：`VoteUpCount`/`CommentCount`/`EditTime` 均有效，方向 `asc`/`desc` 均有效，区间语法 `(min,)` 生效，非法字段返回 `10001 invalid SortBy field`。
- `zhihu_search` 的 `Filter` **只认 `publish_time`**；`host` 仅 `global_search` 支持，且明确拒绝知乎域名。
- `SortBy` 在 `global_search` 上疑似被忽略，故不向该工具暴露。
- **失败调用不消耗额度**（`10001`/`30001` 均不计费），因此重试无额度成本。
- `HasMore` 在站内搜索恒为 false。

## 替代方案

- **按文档实现，删掉 `compileSortBy`**：会砍掉一个真实可用的能力，模型失去按点赞数筛选的手段。
- **保留 `compileSortBy` 但不验证**：若语法错误会把 `10001` 暴露给模型，正是红线 5 要防的幻觉。
- **按旧口径（10/天）设计缓存**：会让缓存的必要性被高估，令牌桶参数失去意义。

## 影响

- 缓存从「必需」降级为「性能优化」；令牌桶仍保留，用于防止一次对话内突发打满额度。
- `Filter` 编译器必须按端点分两套语法，不能共用。
- 探测消耗额度：`zhihu_search` 11 次、`global_search` 2 次（总量 5000/天）。
